01

Performance vs Scalability

Learning objective: Tell a slow-system problem from a growth-under-load problem.

Core ideaPerformance is the work done by one system under one load. Scalability is how performance changes when resources or load change.

A performance problem exists when one request takes too much time. A scalability problem exists when the system works for one user but fails under a larger load.

A scalable design gains useful capacity when you add resources. The gain does not need to be perfect. The design must avoid a new shared bottleneck.

Ask which axis will grow. The axis can be request rate, data size, number of users, or geographic distance.

Diagnosis path

Workload
→
Measure one system
→
Add resources
→
Measure capacity
If the added resource does not add useful capacity, find the shared bottleneck.

Terms

Four terms to keep separate
TermMeaningTypical action
PerformanceHow much work the system completes, and how fast it completes it.Reduce work or improve the slow path.
ScalabilityHow system performance changes as resources or load increase.Remove shared bottlenecks and scale the right part.
Vertical scalingUse a larger machine.Add CPU, memory, storage, or network capacity to one node.
Horizontal scalingUse more machines.Split work across nodes. Keep shared state outside workers when possible.

Small example

An API takes 300 ms with one request. It takes 3 seconds with 1,000 requests per second. The single-request performance is acceptable. The system has a scalability problem.

An API takes 3 seconds with one request. It takes 3 seconds with ten requests per second. The main problem is performance. Scaling out may not fix the slow request.

AskWhich workload axis grows?
MeasureWhat changes after a resource is added?
FindWhich component stays shared?

AWS mapping

Use: Amazon EC2 for compute, an Application Load Balancer for traffic, and EC2 Auto Scaling for horizontal capacity.

Inside AWS: Set a target metric, add instances in more than one Availability Zone, and measure latency, error rate, and saturation with CloudWatch.

Watch: More instances do not fix a slow query or a shared database bottleneck. Test the complete request path.

AWS Performance Efficiency Pillar

Interview question

Prompt: Design a system that scales to millions of users on AWS. Start with one service. Show what changes when traffic grows.

Look for: A measured bottleneck, a scale-out step, stateless workers, and a plan for shared state.

Public interview exercise: System Design Primer · Scaling on AWS.

Recall check

A service is fast for one user but slow for many users. Which problem is likely?

Answer: A scalability problem.

Security

Learning objective: Protect identity, data, and service boundaries in the request path.

Core ideaAuthentication answers who the caller is. Authorization answers what the caller may do. Encryption protects data in transit and at rest.

Use least privilege. Give a component only the permissions it needs. Separate user identity from service identity. Record security events without recording secrets.

Use TLS for data in transit. Hash passwords with a password hashing function. Encrypt sensitive data at rest. Store secrets in a managed secret store, not in source code.

Validate input at every trust boundary. Add rate limits and abuse controls. A firewall can reduce traffic. The application must still enforce authorization.

AWS mapping

Use: AWS IAM for service permissions, Amazon Cognito for user identity, AWS KMS for encryption keys, and AWS WAF for request filtering and rate controls.

Inside AWS: Use IAM roles instead of long-lived keys. Encrypt storage and queues. Put secrets in Secrets Manager or Systems Manager Parameter Store. Log access and denied actions.

Watch: A WAF rule is not authorization. The service must check the caller's permission for the requested object and action.

AWS Security Pillar

Interview question

Look for: Authentication, authorization, encryption, key handling, audit logs, token scope, rate limits, and data minimization.

Public interview exercise: System Design Primer · Mint.com.

Recall check

What is the difference between authentication and authorization?

Answer: Authentication identifies the caller. Authorization checks the caller's allowed action.

Back-of-Envelope Estimation

Learning objective: Turn a product statement into rough traffic, storage, and capacity numbers.

Core ideaAn estimate exposes scale assumptions. It does not need exact values. It must show units and order of magnitude.

Start with users, active fraction, actions per user, peak multiplier, payload size, and retention. Convert the values to requests per second, bytes per second, and bytes stored.

Separate average from peak. Separate reads from writes. Add replication, indexes, metadata, and headroom. State what the estimate does not include.

requests/second = active users × actions/user/second
storage         = writes/second × bytes/write × retention
bandwidth       = requests/second × average payload
Estimate checklist
ValueExample questionUse
UsersHow many total and active users?Base workload.
RateHow many reads and writes per active user?QPS and worker capacity.
SizeHow large is one request or record?Bandwidth and storage.
RetentionHow long do records remain?Total storage and deletion work.

Use powers of two as a memory aid: 1 KB is about 1,000 bytes, 1 MB is about 1,000 KB, and 1 GB is about 1,000 MB for a rough interview estimate. Keep the same unit through the calculation.

AWS mapping

Use: AWS Pricing Calculator for a cost model, CloudWatch for observed workload, and Service Quotas for service limits.

Inside AWS: Convert QPS and storage estimates into instance count, database capacity, queue consumers, object storage, and transfer. Then compare the estimate with measured metrics.

Watch: An AWS service quota is not the same as a performance target. Load test the path and monitor the bottleneck.

AWS Pricing Calculator

Interview question

Prompt: Design Amazon's sales ranking by category feature. Estimate event rate, ranking storage, update delay, and read traffic.

Look for: A stated unit, peak factor, batch or stream choice, approximate storage, and a result that can be checked.

Public interview exercise: System Design Primer · Sales ranking.

Recall check

Why estimate peak traffic separately from average traffic?

Answer: Capacity must handle the high period even when average traffic is lower.

Communication

Learning objective: Define a request contract and the failure behavior between client and service.

Core ideaA communication protocol defines how two components name work, carry data, report success, and report failure.

HTTP uses a method, a target, headers, and an optional body. A response uses a status code, headers, and an optional body. The client and service must agree on these fields.

Keep a request id across the path. Set connection, request, and dependency timeouts. Return an error that the caller can act on. Retry only an operation that is safe to retry.

HTTP is often stateless at the protocol layer. The service can still use a session token or a shared session store. Stateless workers make scale-out easier.

VersionAccept old and new fields during a migration.Lets clients and services change at different times.

AWS mapping

Use: Amazon API Gateway for managed public HTTP APIs. Use an Application Load Balancer when HTTP routing to targets is the main need.

Inside AWS: Define routes, authentication, throttling, request validation, timeouts, and access logs. Put the service behind private networking when the public edge is separate.

Watch: API Gateway can reject a request before the application. Expose useful status codes and request ids so clients can recover.

Amazon API Gateway Developer Guide

Interview question

Prompt: Design Pastebin.com or Bit.ly. Define the create-short-link and resolve-short-link APIs. What happens when a client retries?

Look for: Resource names, status codes, idempotency, redirects, rate limits, and versioning.

Public interview exercise: System Design Primer · Pastebin / Bit.ly.

Recall check

Why is an idempotency key useful?

Answer: It lets the service recognize a repeated request and avoid applying the same operation twice.

TCP vs UDP

Learning objective: Select a transport from the cost of loss, ordering, and connection setup.

Core ideaTCP gives an ordered, reliable byte stream. UDP sends datagrams without the same delivery and ordering guarantee.

TCP retransmits lost data and controls the sending rate. This is useful when every byte matters. It adds connection state and can wait for missing data.

UDP lets the application choose what to do with loss and ordering. This is useful when a new update is more useful than an old update, such as some voice, video, and game traffic.

The transport is only one part of the design. The application still needs timeouts, authentication, rate limits, and a failure policy.

AWS mapping

Use: A Network Load Balancer for TCP or UDP targets. Use AWS Global Accelerator when global entry points and fast regional failover matter.

Inside AWS: Define listeners and target health checks. Place tasks or instances in multiple Availability Zones. Track connection count, new connections, and target errors.

Watch: A UDP listener does not make the application reliable. Add sequence numbers, expiry, or application acknowledgements when required.

AWS Network Load Balancer

Interview question

Prompt: Design a chat server. Which traffic needs ordered delivery, and which traffic can use a lower-latency transport?

Look for: Message durability, reconnect behavior, ordering scope, presence state, fan-out, and abuse control.

Public design exercise listed by the System Design Primer.

Recall check

When is UDP a reasonable choice?

Answer: When the application can tolerate or repair loss and a fresh update is more useful than an old one.

RPC vs REST

Learning objective: Choose a service interface that keeps the contract clear for its callers.

Core ideaREST models resources and uses HTTP semantics. RPC models operations and calls named methods. Both need a precise contract.

REST works well for public APIs with resources, standard methods, cache rules, and human-readable requests. RPC can make internal calls explicit and efficient with a typed schema.

Use an interface definition. State field types, required fields, error codes, timeout behavior, and compatibility rules. A service contract is a dependency.

Do not choose by label alone. Measure payload size, call count, latency, client variety, and the need for streaming.

AWS mapping

Use: API Gateway REST or HTTP APIs for public interfaces. Run gRPC services on ECS or EKS behind an Application Load Balancer or Network Load Balancer as the protocol needs.

Inside AWS: Register service names with Cloud Map when callers need discovery. Use IAM or a service identity. Set connection, request, and dependency timeouts.

Watch: A managed gateway does not define a good contract. Keep schemas, version rules, and error behavior in the service code and documentation.

API Gateway HTTP APIs and REST APIs

Interview question

Look for: Document state, edit ordering, presence, conflict handling, streaming or push updates, and contract versioning.

What must every RPC or REST interface define?

Answer: Inputs, outputs, errors, timeout behavior, and compatibility rules.

Database

Learning objective: Choose a data store from the data model, access pattern, and correctness rule.

Core ideaA database choice follows the data and the query. Start with reads, writes, relationships, scale, and failure behavior.

A relational database stores structured rows and relationships. SQL gives joins and transactions. A non-relational database can use a document, key-value, column, or graph model. It can scale well for known access patterns.

An index makes a query faster by storing a structure for lookup. The index uses storage and makes writes slower. Add an index for a measured query.

A replica copies data. A shard splits data. Replicas help read scale and recovery. Shards help write and storage scale. Both add routing and operational work.

Database choice

Read scale from one sourceRead replicasReplica lag can produce stale reads.
Data and write scale exceed one nodeSharding or a distributed databaseCross-shard queries and transactions cost more.

Write the access patterns before the schema. For a feed, ask for posts by user, posts by time, and posts for a follower. For financial data, ask where atomicity and audit history are required.

AWS mapping

Use: Amazon Aurora or Amazon RDS for relational data. Use DynamoDB for key-value or document access with a known partition key.

Inside AWS: Add Aurora readers for read scale. Use a writer endpoint and reader endpoints. In DynamoDB, design the partition key, sort key, and capacity around the query.

Watch: A read replica does not remove write limits. A DynamoDB partition key with hot values can still create a bottleneck.

Amazon Aurora high availability

Interview question

Prompt: Design Mint.com. Which data belongs in a relational database, which queries need indexes, and where can reads be stale?

Look for: User and account data, transaction history, aggregation jobs, privacy, auditability, and the read/write path.

Public interview exercise: System Design Primer · Mint.com.

Recall check

What is the difference between a replica and a shard?

Answer: A replica copies the same data. A shard holds one part of the data.

Cache

Learning objective: Use a cache to reduce repeated work while keeping stale data safe.

Core ideaA cache is a faster copy of data. The source of truth stays in durable storage.

In cache-aside mode, the application reads the cache first. On a miss, it reads the database and writes the result to the cache. On a write, it updates the database and removes or updates the cache entry.

Every entry needs a key, a value, a TTL, and an eviction rule. The cache key must include every input that changes the response.

Many misses at one time can overload the database. Add request coalescing, jittered expiry, a stale value policy, or a warm-up step when the risk is real.

Cache-aside path

Client
→
Cache
→
Hit: return
Miss: read the database, return the value, and store it with a bounded TTL.
Cache controls
ControlQuestionFailure if missing
KeyWhich request inputs identify one value?Wrong data is returned.
TTLHow long may the value be stale?Old data remains too long.
EvictionWhich item leaves when memory is full?Useful items are removed or memory fills.
InvalidationHow does a write remove old data?Reads return a value that should be changed.

A cache improves latency and reduces database work. It also creates a second state. State the allowed staleness and the behavior when the cache is empty or unavailable.

AWS mapping

Use: Amazon ElastiCache for Redis or Memcached. Use CloudFront for edge content. Use DynamoDB Accelerator only when its access pattern fits.

Inside AWS: Use a cache-aside client with a bounded TTL. Size nodes for memory and network. Add replication and automatic failover when the cache failure path is defined.

Watch: ElastiCache is not the durable source of truth. Decide whether a cache outage means slower reads, rejected writes, or reduced features.

Amazon ElastiCache

Interview question

Prompt: Design a key-value store for a search engine. How do you cache popular queries and stop one expired key from causing a database storm?

Look for: Cache key, TTL, eviction, negative results, invalidation, stampede control, and a source of truth.

Public interview exercise: System Design Primer · Key-value store.

Recall check

What must happen after a database write when the old value is cached?

Answer: Update or invalidate the cache entry according to the correctness rule.

Asynchronism

Learning objective: Move slow or independent work off the user request path.

Core ideaAsynchronous work lets a producer continue before a consumer finishes. A queue holds work between the two.

The producer writes a message. A worker reads the message and performs the job. The producer does not need to wait for the worker.

Asynchronism adds delay and delivery uncertainty. A message may be delivered more than once. The worker must be idempotent, or it must use a deduplication rule.

Set a visibility timeout, retry limit, and dead-letter path. Monitor queue depth and oldest message age. These values show whether work is keeping up.

Job path

Producer

AWS mapping

Use: Amazon SQS for queues, Amazon SNS for fan-out, Amazon EventBridge for event routing, and AWS Step Functions for visible workflows.

Inside AWS: Configure visibility timeout, redrive policy, dead-letter queue, encryption, and CloudWatch alarms. Scale consumers from queue depth and message age.

Watch: SQS standard queues provide at-least-once delivery. Design the consumer so duplicate processing is safe.

Amazon SQS Developer Guide

Interview question

Prompt: Design a web crawler. How do you distribute URLs to workers, limit work per host, retry failures, and avoid crawling one URL twice?

Look for: Durable queue, URL normalization, deduplication, per-host fairness, idempotent storage, and a dead-letter path.

Public interview exercise: System Design Primer · Web crawler.

Recall check

Why must a queue consumer expect duplicate messages?

Answer: Many distributed queues use at-least-once delivery. A retry can deliver a message again.

Latency vs Throughput

Learning objective: Measure time per result and results per unit of time as different values.

Core ideaLatency is the time for one action. Throughput is the number of actions completed in a unit of time.

Latency answers: “How long does this request take?” Throughput answers: “How many requests finish each second?”

A system can have high throughput and high latency. A batch system can process many jobs per hour while each job waits a long time.

Set a latency limit that users can accept. Then increase throughput without crossing that limit.

Two measurements of one pipeline

Request starts
→
Work runs
→
Response returns
Latency is the length of this path. Throughput is the number of completed paths per second.

Terms

Time and rate
TermUnitQuestion
LatencyMilliseconds, seconds, or hours.How long does one action take?
ThroughputRequests per second, jobs per hour, or bytes per second.How many actions finish in a unit of time?
CapacityMaximum useful throughput under a stated limit.How much work can the system accept before a limit breaks?

Small example

An assembly line takes 8 hours to build one car. Its latency is 8 hours per car. It builds 120 cars per day. Its throughput is 120 cars per day.

Adding workers can increase throughput. It may also increase coordination time. Measure both values.

latency   = time for one result
throughput = results / unit of time

AWS mapping

Use: CloudWatch metrics for request latency, throughput, errors, and saturation. Use AWS X-Ray when you need a trace across services.

Inside AWS: Put a latency objective on the user path. Measure p50, p95, and p99. Do not use only an average.

Watch: A queue can increase throughput while it increases wait time. Keep synchronous and asynchronous paths separate in the design.

AWS X-Ray developer guide

Interview question

Prompt: Design a web crawler. How do you increase crawl throughput without making one fetch wait forever?

Look for: Bounded workers, queues, per-host limits, retry policy, and separate fetch latency from total crawl rate.

Public interview exercise: System Design Primer · Web crawler.

Recall check

Can a system have high throughput and high latency?

Answer: Yes. Batch processing is one example.

Availability vs Consistency

Learning objective: Explain the CAP trade-off during a network partition.

Core ideaWhen a distributed system has a network partition, it must choose whether to reject or delay some operations, or return a possibly stale result.

Consistency means a read returns the most recent accepted write, or returns an error.

Availability means a non-failing node returns a response within a reasonable time.

Partition tolerance means the system continues to operate when nodes cannot communicate.

Network partitions can occur. Therefore, the practical choice during a partition is between consistency and availability. This choice depends on the business rule.

Decision during a partition

Client request
→
Node A / Node B
→
Network link breaks
CP: wait or return an error. AP: return a local value and accept possible staleness.
CP and AP behavior
ChoiceDuring a partitionUse when
CPWait for coordination or return an error.Atomic reads and writes are required.

Use the business rule to choose. A bank balance may require CP behavior. A shopping cart or social reaction may allow AP behavior.

AWS mapping

Use: Amazon DynamoDB for a managed distributed key-value store. Use regional tables or global tables only after you state the consistency rule.

Inside AWS: Keep strongly consistent reads and transactional writes in the scope supported by the service. Use asynchronous multi-Region replication when stale reads are acceptable.

Watch: “DynamoDB is AP” is too broad. State the table, Region, read mode, write mode, and failure case.

DynamoDB global tables

Interview question

Prompt: Design the Twitter timeline and search. During a partition, which result may be stale, and which result must be correct?

Look for: A clear business rule. Feed freshness can tolerate delay. A delete, privacy rule, or account state may need stronger control.

Public interview exercise: System Design Primer · Twitter timeline and search.

Recall check

What changes when a network partition occurs?

Answer: The system must choose between strict consistency and always returning a response. Partition tolerance is not optional for a distributed system.

Consistency Patterns

Learning objective: Choose a consistency pattern for a replicated value.

Core ideaReplication creates copies. A consistency pattern defines what a reader may see after a write.

When data has several copies, the copies can update at different times. The system must define the allowed view for a reader.

Use a read-after-write question. After a client writes a value, what may the next read return?

Replicated write and read

Write replica A
→
Replicate to B
→
Read B
The pattern controls the result when the read occurs before replication finishes.
Three consistency patterns
PatternRead after writeTypical useCost
WeakThe read may see the write or may not see it.Real-time audio, video, or multiplayer state.Low coordination. Data can be lost or missed.
EventualThe read will see the write after propagation completes.DNS, email, search indexes.Low write coordination. Reads can be stale for a period.
StrongThe read sees the accepted write.Transactions, files, and relational databases.More coordination, latency, or reduced availability.

Eventual consistency requires a condition. If writes stop and replication continues, copies converge to the same value. If new writes keep arriving, convergence may not occur.

Do not choose a pattern by habit. State the user-visible error that stale data would cause.

AWS mapping

Use: Amazon Aurora or Amazon RDS when relational transactions matter. Use DynamoDB when access patterns fit partition-key reads and writes.

Inside AWS: Use a writer endpoint for writes and reader endpoints or replicas for read scale. Document replica lag. Select a DynamoDB read mode that matches the required guarantee.

Watch: A read replica is not a strong-consistency guarantee. The application must know what stale data means.

DynamoDB read consistency

Interview question

Prompt: Design a key-value store for a search engine. How do you keep replicas useful when a read reaches a replica that is behind?

Look for: Read and write paths, replication delay, failure behavior, repair, and a statement of the allowed stale window.

Public interview exercise: System Design Primer · Key-value store.

Recall check

What does eventual consistency promise?

Answer: A read will see the write after the data has propagated, if updates stop and propagation continues.

05

Availability Patterns

Learning objective: Explain how failover, replication, and redundancy change service availability.

Core ideaHigh availability uses more than one path or copy. The extra path helps only when it can take over and the service can use it.

Failover moves service from a failed node to a standby node. In active-passive mode, one node handles traffic. In active-active mode, both nodes handle traffic.

Replication keeps more than one copy of data or service state. The copy can be synchronous or asynchronous. The choice affects data loss, latency, and recovery.

Availability is often written as a percentage. Three nines means 99.9% availability. Four nines means 99.99% availability.

Availability in numbers
TargetAllowed downtime per yearAllowed downtime per day
99.9%About 8 hours 46 minutes.About 1 minute 26 seconds.
99.99%About 52 minutes 36 seconds.About 8.6 seconds.
99.999%About 5 minutes 16 seconds.About 0.87 seconds.
 
sequence:  A_total = A_foo × A_bar
parallel:  A_total = 1 - (1 - A_foo) × (1 - A_bar)

For two 99.9% components in sequence, total availability is about 99.8%. Both components must work.

For two 99.9% components in parallel, total availability is about 99.9999%. At least one component must work.

These formulas describe independent component availability. They do not prove that the failover process is correct. Test health checks, promotion, state recovery, and client retry behavior.

AWS mapping

Use: Multi-AZ deployment for compute and data. Use Elastic Load Balancing health checks and Route 53 health-based routing when traffic must move.

Inside AWS: Define recovery time objective and recovery point objective. Test failover, data promotion, DNS behavior, and client retries.

Watch: More copies can increase write latency and split-brain risk. Redundancy without a tested recovery path is not availability.

Domain Name System

Learning objective: Trace a domain name to an IP address and explain the role of caching.

Core ideaDNS maps a name such as www.example.com to an address that a client can use.

A browser asks a recursive resolver for an address. If the resolver has no cached answer, it asks the root name server, the top-level domain server, and the authoritative name server.

The resolver caches the answer for the record's time to live, or TTL. A longer TTL reduces lookup work but keeps old data longer.

DNS can also return different addresses for traffic steering. A service can use weighted, latency-based, or geographic routing. The routing policy does not remove the need for health checks and failure planning.

AWS mapping

Use: Amazon Route 53 for hosted zones, DNS records, health checks, and routing policies.

Inside AWS: Point a domain to CloudFront, an Application Load Balancer, or an API Gateway API. Select a routing policy. Set TTL with the failure and change window in mind.

Watch: DNS changes are cached. A low TTL can increase resolver work. A high TTL can slow failover.

Content Delivery Network

Learning objective: Explain why an edge cache reduces origin work and user distance.

Core ideaA CDN stores copies at edge locations. A user can receive a cached object from an edge location near the user.

A cache hit returns an object without asking the origin. A cache miss asks the origin and can store the result for later requests.

Static assets such as images, CSS, JavaScript, and video are common CDN content. Dynamic content needs a rule that makes caching safe.

PullThe CDN fetches content after the first request.Less upload work. The first request can be slower and stale data needs a TTL or purge.

Cache policy is part of correctness. Set the cache key, TTL, revalidation rule, and purge rule. Do not cache user-specific content under a shared key.

AWS mapping

Use: Amazon CloudFront in front of an S3 bucket, an Application Load Balancer, or a custom origin.

Inside AWS: Define a cache policy and origin request policy. Use versioned asset names or invalidation when content changes. Keep private content out of shared cache keys.

Watch: A CDN reduces origin traffic. It does not remove origin capacity, invalidation, or authorization work.

What happens on a cache miss?

Load Balancer

Learning objective: Explain how a load balancer selects a healthy target and supports scale-out.

Core ideaA load balancer receives traffic, chooses a target, and avoids targets that fail health checks.

A load balancer can spread requests across application servers. It can remove an unhealthy server from the pool. It can also terminate TLS and keep a stable public address.

Horizontal scaling adds more workers. Workers should be stateless when possible. Store sessions and durable data in a shared data system.

Use round robin when targets are similar. Use least loaded when target capacity or current work differs. Use session persistence only when the application cannot keep session state in a shared store.

A single load balancer can become a single point of failure. Use more than one load balancer and define how clients reach the healthy one.

AWS mapping

Use: Elastic Load Balancing. Choose an Application Load Balancer for HTTP routing, a Network Load Balancer for high-performance TCP or UDP, or a Gateway Load Balancer for network appliances.

Inside AWS: Put targets in multiple Availability Zones. Use target groups, health checks, listener rules, and Auto Scaling. Keep application sessions external to targets.

Watch: Health checks must test useful service health. A process that answers a port can still be unable to serve real requests.

Why must a horizontally scaled worker be stateless when possible?

Reverse Proxy

Learning objective: Explain how a reverse proxy presents one public interface for internal services.

Core ideaA reverse proxy receives a public request and forwards it to an internal server. The client does not need to know the internal server address.

A reverse proxy can work with one backend server. A load balancer usually distributes work across several equivalent targets. One product can do both jobs.

Common proxy work includes TLS termination, compression, caching, static file serving, connection limits, and request filtering.

AWS mapping

Use: CloudFront for edge work, an Application Load Balancer for HTTP routing, or API Gateway for a managed public API boundary. Run NGINX on ECS or EC2 when its policy is required.

Inside AWS: Terminate TLS at the selected boundary. Forward only the headers and paths that the internal service needs. Keep the boundary redundant.

Watch: Each proxy adds a hop. Measure connection reuse, header limits, buffering, timeout values, and body size limits.

Application Layer

Learning objective: Separate public web handling from application work and service discovery.

Core ideaSeparate layers when they have different scaling, release, or failure needs. The application layer runs business logic and calls data services.

The web layer can handle connections and static content. The application layer can handle business rules and API requests. Each layer can scale on its own.

A microservice is a small service that can be deployed independently and owns a business capability. The network call adds latency and failure modes. Use a service boundary only when the boundary has value.

Service discovery maps a service name to healthy service instances. A service registry stores addresses and health state. A resolver or proxy returns a usable target.

Start with a clear business capability. Do not split a system only because a smaller service sounds modern. A modular monolith can keep local calls and still preserve useful boundaries.

AWS mapping

Watch: Service discovery finds an instance. It does not make a bad dependency fast or reliable.

Interview Method

Learning objective: Lead an open design discussion from requirements to one justified architecture.

Core ideaA good interview design is a sequence of stated assumptions, simple components, measured constraints, and explicit trade-offs.

First, define the users and the most important actions. Ask about read and write volume, data size, latency, availability, geography, privacy, and retention.

Second, draw the high-level request path. Third, estimate the scale. Fourth, choose storage and failure behavior. Fifth, deep dive into the component that limits the requirement.

End by naming the main bottleneck, the next improvement, and the trade-off. A design is easier to review when another engineer can test its assumptions.

Capstone: A System That Scales

Learning objective: Combine the book's patterns into one design and explain why each component exists.

Core ideaScale the request path in stages. Keep durable state explicit. Add a component only when a stated limit requires it.

Start with a client and a public name. Route the name to an edge or load balancer. Send the request to stateless application workers. Use a cache for repeated reads. Use a database for durable state. Put slow work on a queue.

For growth, add replicas or shards after measuring the limit. For failure, use more than one Availability Zone and define health checks, recovery, and data loss. For security, authenticate the caller and authorize each action.

This is a starting architecture. It is not a promise of capacity. The numbers, workload, and correctness rules decide the final design.
